# 파일럿 서버 설정

앱은 이 설정이 하나도 없어도 정상 동작한다. 학습·복습·읽기는 전부 기기 안에서 돌아간다.
아래 설정은 **원격 파일럿 데이터를 회수하고 알림을 보내기 위한 것**이다.

설정하지 않은 상태로 배포하면 `/api/*`는 `store not configured`를 돌려주고,
클라이언트는 조용히 넘어간다.

## 시작 전에 반드시 이것부터

```
GET /api/health
```

원칙은 **사용자에게는 조용히 degrade, 운영자에게는 시끄럽게 실패**다.
`/api/events`는 설정이 없어도 200을 준다. 앱이 깨지지 않게 하려면 그래야 한다.
그런데 그러면 환경변수를 깜빡한 배포에서 모든 요청이 성공하고 데이터는 0건인 상태를
아무도 모른 채 파일럿이 끝날 수 있다. 그걸 막는 게 이 엔드포인트다.

하나라도 빠져 있으면 503과 누락 목록을 준다. **파일럿 시작 전에 200인지 확인한다.**
비밀값 자체는 돌려주지 않고 설정 여부만 알려 준다.

수집(`store` + `EXPORT_TOKEN`)이 안 되면 503이다. 알림은 선택이므로 `notifying`
필드로만 표시하고 200을 막지 않는다.

## 서버가 보관하는 것과 보관하지 않는 것

| 보관한다 | 보관하지 않는다 |
| --- | --- |
| 익명 학습자 id (기기에서 생성) | 용어별 정답 횟수·복습 날짜 |
| 표준시 | 어떤 용어를 알고 모르는지 |
| 마지막으로 권장 분량을 마친 날 | 로그인 정보, 이름, 연락처 |
| 마지막 학습일, 연속 일수 | |
| 알림 구독 정보, 마지막 발송일 | |
| 이벤트 로그 (문항·소요시간·정답 여부) | |

학습 상태의 source of truth는 기기의 localStorage다. 서버와 맞추지 않는다.
그래서 서버가 죽어도 학습이 멈추지 않고, 실패한 요청 하나가 진도를 되돌릴 수도 없다.

## 한계를 먼저 적는다

익명 id는 localStorage에 있다. 그래서 **브라우저 데이터를 지우거나 기기를 바꾸면
같은 사람으로 이어지지 않는다.** 서버가 있으면 데이터가 안 사라진다고 가정하면 안 된다.
다중 기기 연속성은 계정을 만들어야 풀리는 문제이고 이번 범위가 아니다.

## 1. 저장소 (Upstash Redis / Vercel KV)

Vercel 프로젝트에 Upstash Redis를 연결하면 아래 두 값이 자동으로 주입된다.

```
KV_REST_API_URL
KV_REST_API_TOKEN
```

SDK를 설치하지 않고 REST로 호출한다. 파일럿 규모(수십 명)에서 이벤트는 하나의
리스트에 쌓아 두면 충분하다.

## 2. 데이터 회수

```
GET /api/export?token=<EXPORT_TOKEN>            # CSV
GET /api/export?token=<EXPORT_TOKEN>&format=json
```

관리자 화면은 만들지 않는다. CSV를 스프레드시트에서 열거나 쿼리로 보면 된다.

```
EXPORT_TOKEN=<임의의 긴 문자열, 16자 이상>
```

**이 값이 없거나 16자 미만이면 `/api/export`는 404를 준다.** `있으면 검사한다`로
쓰면 환경변수를 잊은 배포에서 데이터가 그대로 열린다. 잊어버리는 쪽이 안전한
방향이어야 한다. `/api/cron-nudge`도 `CRON_SECRET`에 같은 규칙을 쓴다.

### 들어오는 값에 대한 제한

`/api/events`와 `/api/daily-status`는 참가자 브라우저가 직접 호출하므로 공개된다.
들어오는 값을 그대로 믿지 않는다.

| | 상한 |
| --- | --- |
| 익명 id | `[A-Za-z0-9_-]{8,64}` 형식만 |
| 한 번에 보내는 이벤트 | 200개 |
| 본문 크기 | 128KB |
| payload 키 / 문자열 | 20개 / 200자 |
| IP당 호출 | 분당 30회 |
| 알림 구독 정보 | https endpoint, 길이 제한, 필요한 필드만 골라 저장 |

호출량 제한은 서버리스 인스턴스마다 메모리가 따로 있어 완전한 방어가 아니다.
한 인스턴스에 쏟아지는 반복 호출만 막는다. 파일럿 규모에서는 이 정도면 충분하다.

### 이벤트 중복

각 이벤트에 `eventId`(UUID)와 `eventSchemaVersion`이 있다. 전송이 실패하면 커서를
올리지 않고 다시 보내므로 같은 이벤트가 두 번 닿을 수 있다. **집계할 때 `eventId`로
중복을 걸러낸다.** CSV에도 두 열이 나온다.

### 완료 상태는 이벤트보다 중요하게 다룬다

이벤트 몇 개 유실은 괜찮다. 그런데 완료 사실이 서버에 닿지 않으면 그날 저녁에
다 한 사람에게 독촉이 간다. 그래서 완료 상태는 실패하면 기기에 남겨 두고, 앱을
다시 열 때·화면이 다시 보일 때·온라인으로 돌아올 때 재전송한다.

## 3. 알림 (선택)

```
VAPID_PUBLIC_KEY
VAPID_PRIVATE_KEY
VAPID_SUBJECT=mailto:you@example.com
CRON_SECRET=<임의의 긴 문자열>
VITE_VAPID_PUBLIC_KEY=<VAPID_PUBLIC_KEY와 같은 값>
```

키 생성:

```bash
npx web-push generate-vapid-keys
```

`VITE_` 접두사가 붙은 값만 클라이언트 번들에 들어간다. private key는 절대 붙이지 않는다.

발송 조건은 셋뿐이다. 여기에 개인별 최적 시각 예측 같은 것을 붙이지 않는다.

1. 알림을 허용했다
2. 오늘 권장 분량을 아직 안 했다
3. 오늘 아직 알림을 안 보냈다

추가로 같은 공백 구간에서 같은 문구를 두 번 보내지 않는다. 3일 쉰 사람에게
`금융문맹 되어가는 중…`을 매일 보내면 유머가 아니라 잔소리가 된다.

크론은 매일 KST 20시(UTC 11시)에 한 번 돈다. `vercel.json`에서 바꾼다.

### iOS 제약

아이폰에서는 홈 화면에 추가한 뒤에만 알림을 받을 수 있다. 그래서 파일럿 참가자 중
알림을 받는 사람과 받지 못하는 사람이 섞인다. **재방문율을 하나로 묶어 알림 효과라고
해석하면 안 된다.** 분석에서 두 집단을 나눈다.

## 4. 삭제와 보관 기간

학습 기록 화면의 `기록 지우기`는 네 가지를 함께 한다.

1. 알림 구독 해지
2. 서버의 학습자 기록 삭제
3. **익명 id 새로 발급**
4. 기기 데이터 삭제

3번이 있어야 `지웠다`는 말이 사실이 된다. id를 그대로 두면 지운 뒤의 기록이 지운
이전 사람에 다시 붙는다. 지운 시점 이전과 이후는 다른 사람으로 센다.

운영자가 직접 지울 때는 아래를 쓴다.

```
DELETE /api/daily-status?learnerId=<id>
```

### 보관 기간

이벤트 로그는 익명 id로만 묶여 있어 개별 삭제 대상이 아니다.

| 데이터 | 보관 |
| --- | --- |
| 이벤트 로그 | 파일럿 종료 후 30일. 그 뒤 `voca:events` 키 삭제 |
| 학습자 기록 (알림용) | 파일럿 종료 시 즉시 삭제. `voca:learner:*` |
| 알림 구독 정보 | 발송이 404/410으로 실패하면 그 즉시 삭제 |

파일럿 종료 시 Upstash에서 위 키를 지운다. 종료일을 정해 두고 지나가지 않게 한다.
